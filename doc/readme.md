# Справочные материалы

## grpc

### генерация клиентской части
```shell
protoc --go_out={target_path} \
 --go-grpc_out=require_unimplemented_servers=false:./{target_path}/ \
 {path_to_proto_file}
```

### генерация сервера
```shell
 protoc --go_out={target_path} \
 --go-grpc_out={target_path} \
  {path_to_proto_file} 
```

## Мелкие замечания

* Docker конфигурация для сервисов почти всегда идентичная, потом будет приложен семпл Dockerfile
* В случае использования yaml для хранения конфигурации стоит учитывать при локальной разработке, что библиотека ищет начиная от корня модуля, а не точки его вызова
* HealthCheck у rabbitMQ обязателен, поскольку его контейнер стартует позже консьюмера, а благодаря такому трюку сервис будет ожидать успешного хелсчека
* Интерфейсы по месту применения в файле dependencies.go - чисто вкусовщина, если вы привыкли декларировть контракты централизованно - все в ваших руках
* Указатели - не панацея, если вы храните у себя пачку указателей(например usecase что хранит по факту список зависимостей-интерфейсов), то нет смысла оперировать указателем на родительскую структуру, куда дешевле ее копировать, нежели алочить на хип
* Горутины - не спасение, если у вас слишком долго выполняется задача, постарайтесь изначально оптимизировать ее, нежели бездумно кидать в фоновый процесс и отдавать клиенту 200
* Походы в базу в циклах - плохо. Стоит избегать по возможности таких кейсов, благо есть инструмент a = ANY ($1::ANY[])
* Синк пулы - не обязанность, в примере они использовались лишь для демонстрации возможностей, объективно - выгоднее создавать свои воркер пулы
* Структура проекта - не серебрянная пуля, не эталон, не как обязанны делать, лишь моя вкусовщина, если неважно - можно слизать.
* Отсутствие структуры в productservice и в notificationservice - результат лени, в итоговом проекте единая структура должна быть соблюдена везде
